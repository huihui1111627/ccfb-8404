# 公交客流 OD 推算平台

> 刷卡只有上车、没有下车；GPS 与站点分属不同系统。本平台把三套数据对齐，
> 用**出行链证据**推断下车站，产出分时段 OD、断面客流与满载率，并用带真值的
> 测试数据量化准确率。

Python + Polars 实现，FastAPI 提供接口，浏览器控制台（Leaflet 地图）无需构建步骤。

---

## 1. 快速开始

```bash
python3 -m venv --system-site-packages .venv
.venv/bin/python -m pip install polars fastapi "uvicorn[standard]"
.venv/bin/python -m app.cli serve --port 8404
# 打开 http://127.0.0.1:8404
```

首次启动会自动登记 `data/demo/` 下的演示数据（4 个文件、约 12 万行 GPS），
在页面右上角点「运行推算」即可看到完整结果。也可以用命令行：

```bash
.venv/bin/python -m app.cli demo     # 重新生成演示数据（含真值）
.venv/bin/python -m app.cli run      # 无界面跑一次推算
.venv/bin/python -m app.cli report cli_run
```

> 运行环境为「普通笔记本」量级：12 万条 GPS + 7 千条刷卡，单次推算约 1 秒，
> 内存占用 < 300 MB。

## 2. 页面与功能

| 页面 | 作用 |
|------|------|
| **总览** | 关键指标、准确率、高峰断面 Top5、清理告警 |
| **数据导入** | 刷卡 / GPS / 站点 / 真值四类数据上传，字段映射自动识别并可修改 |
| **站点匹配** | 刷卡记录 ↔ 车辆停站事件明细，停站事件识别质量，站点吸附误差 |
| **出行链** | 每张卡的完整出行链；下车站推算方式、置信度、不确定标记 |
| **OD 矩阵** | 分时段 / 线路 / 方向 OD，地图上按客流强度绘制流向，可导出 CSV |
| **指标看板** | 断面客流、站点上下客量、满载率、清洁质量与准确率分项 |
| **方案对比** | 勾选 2–4 次运行，对比指标与参数差异，定位参数影响 |
| **参数设置** | 时间阈值、清洗规则、时段划分，改完直接重算并保存为新运行 |

### 需求映射

1. **刷卡 / GPS / 线路站点导入，字段映射可配** — 中英文表头自动识别（`交易时间`、`tap_time` 等），
   支持 CSV/XLSX/Parquet/JSON、逗号/制表符分隔、多种时间格式；映射可在预览弹窗里改。
2. **刷卡时间对上车辆 GPS 推出上车站** — GPS 先吸附到线路站点，识别停站事件（到/离时刻），
   再把刷卡时间匹配到「停站窗口」内的车辆与站点。有车载机编号时作为硬约束。
3. **按出行链推下车站，推不出的标记** — 逐卡顺序推理：下一次刷卡同站 → 邻近站（步行可达）→
   返程锚点 → OD 先验兜底。无直接证据的结果标 `uncertain`，界面显示为红色「低」。
4. **识别换乘，时间阈值可调** — 相邻两段出行满足「下车→下次上车」时间窗 + 步行距离即视为一次换乘，
   阈值在参数页可调，重算后换乘次数随之变化。
5. **分时段 OD 矩阵，地图看流向** — 时段可自定义；地图按客流强度配色/线宽，点击线条看明细。
6. **断面客流、站点上下客、满载率** — 按「上客 − 下客」逐站累计得到断面客流，
   除以定员得到满载率，超过 100% 标红。
7. **清洗异常卡、重复刷卡、GPS 漂移** — 重复刷卡（同卡同车/同线路短时二次刷卡）、
   异常卡（无法匹配任何停站）、GPS 漂移点（孤立跳变）均单独统计并展示。
8. **改参数能重算，结果能对比** — 每次运行保存参数与结果快照，对比页并排显示指标与参数差异。

## 3. 算法说明

```
刷卡(AFC)  GPS(AVL)  线路站点
    │          │          │
    │      ①清洗漂移/重复   │
    │          ↓          │
    │     ②吸附站点→停站事件 │
    │          ↓          │
    │     ③切分班次(车次)   │
    └────④匹配上车站────────┘
               ↓
        ⑤出行链推理下车站
        （同站 > 邻近站 > 返程锚点 > OD 先验）
               ↓
        ⑥换乘识别 / 出行链划分
               ↓
        ⑦OD 矩阵 · 断面客流 · 满载率
               ↓
        ⑧与真值比对 → 准确率
```

### 关键设计

- **GPS 先成「停站事件」**：每 10 秒一条定位，按线路站点吸附后切分为连续的「同一站点停留段」，
  过滤掉过短停留与速度异常段。这样刷卡匹配只需查事件表，天然带车辆与方向。
- **下车站候选只取同车后续站点**：乘客必然在本次乘坐的车辆后续停站下车，
  这一约束把候选从「全网站点」压缩到「后续 1–10 站」，也是准确率的根本来源。
- **证据打分而非硬规则**：
  - 下次刷卡就在同一站 → +80（最强证据，实测准确率 97.4%）
  - 下次刷卡在步行可达的邻近站 → +14~34，按距离衰减
  - 当天只有两次刷卡且末次回到首次上车站 → 返程锚点（实测 94% 命中）
  - 没有任何证据 → OD 先验 + 乘车距离先验兜底，**明确标记为不确定**
- **先验从数据本身学习**：某上车站到各站的 OD 频次、站点吸引力、乘车距离分布，
  均从「有证据、已确定」的出行中统计，不使用真值。
- **准确率分开报告**：有证据结果与兜底结果分开统计，避免用兜底结果稀释或粉饰指标。

## 4. 演示数据与准确率

演示数据由 `app/generator.py` 生成，刻意模拟真实的不完美条件：

- 8 条线路（含 1 条环线）、29 辆车、921 个班次、67 个站点
- 2,876 张卡、6,133 条刷卡，其中：漏刷 84、重复刷卡 96、异常时间 67
- 12.4 万条 GPS，其中：漂移点 501、重复时间戳、缺失定位
- 真实出行链来自引力式需求模型（短途出行占多数），带真实下车站真值

当前结果（`python -m app.cli report cli_run`）：

| 指标 | 结果 |
|------|------|
| 刷卡记录 | 6,133 |
| 上车站匹配率 | **99.9%** |
| 上车站准确率（对照真值） | **99.97%** |
| 车辆匹配准确率 | **100.0%** |
| 下车站推算率 | **99.6%** |
| 下车站准确率 · 全部 | **72.1%** |
| 下车站准确率 · 邻近站容差（≤700 m） | **85.4%** |
| 下车站准确率 · 确定结果 | **96.4%** |
| 确定结果占比 | 60.3% |
| 换乘 F1 | **0.98** |
| 重复刷卡召回 | 100% |
| GPS 漂移剔除 | 407 / 501 注入点 |
| 单次运行 | ≈ 1 秒 |

分推算方式准确率：

| 推算方式 | 占比 | 准确率 |
|----------|------|--------|
| 下次刷卡同站 | 2,519 | 97.6% |
| OD 先验兜底（不确定） | 1,777 | 25.9% |
| 返程锚点 | 1,672 | 83.0% |
| 邻近站步行 | 2 | — |

**为什么整体不是 95%**：约 30% 的出行在当天没有任何后续刷卡（单次出行卡、
当天最后一次出行），这类出行在下车站上等价于「从后续站点中猜一个」。
用真值检验，即使在该上车站的历史 OD 分布里取最大概率的站点，上限也只有约 25%。
平台把这类结果单列为「不确定」，而不是把它们混进「确定」指标里；
若只看有直接证据的出行，准确率为 96.4%。
若允许误差落在一站以内（≤700 m），整体准确率为 85.4%——多数「错」只是相邻站，
乘客实际仍在正确区域，运营上可以接受。

## 5. 目录结构

```
app/
  main.py        FastAPI 路由 + 静态页面
  pipeline.py    推算主流程（清洗→停站→匹配→出行链→OD→指标→准确率）
  ingest.py      文件解析、表头识别、字段映射、类型规范化
  generator.py   演示数据生成器（含真值）
  jobs.py        后台任务与进度
  store.py       SQLite 元数据（数据集、映射、运行、参数快照）
  config.py      默认参数、标签
  utils.py       时段表达式、距离、参数校验
  cli.py         命令行入口
  static/        网页控制台（原生 JS + Leaflet，无构建）
data/
  demo/          演示数据（CSV + 真值 + 元信息）
  datasets/      导入的数据（Parquet）
  runs/<id>/     每次运行的 Parquet 结果与 metrics.json
tests/
  test_pipeline.py  46 项 Python 测试（含 API）
  core.test.js      17 项前端工具函数测试
  browser_smoke.py  真实浏览器端到端检查
```

```bash
.venv/bin/python -m pytest tests/test_pipeline.py -q     # 46 passed
node --test tests/core.test.js                           # 17 passed
.venv/bin/python tests/browser_smoke.py                  # 需先启动服务
```

浏览器冒烟测试会真实点击每个页面、检查地图是否画出流向、执行一次参数
改动后的重算，并验证对比页，同时收集控制台错误（有错误即失败）。

测试覆盖的关键场景包括：中英文表头识别、多种时间格式、行向归一化、
越界坐标剔除、重复流水号去重、时段划分（含 Int8 溢出回归测试）、
GPS 漂移识别、极端参数不崩溃、映射修复流程、任务失败信息、API 分页与导出。

## 7. 参数一览

| 参数 | 默认 | 说明 |
|------|------|------|
| `stop_snap_radius_m` | 90 | GPS 吸附站点的最大距离 |
| `gps_speed_max_kmh` / `gps_drift_max_m` | 80 / 120 | 漂移点判定的速度与距离阈值 |
| `min_dwell_sec` / `dwell_speed_kmh` | 8 / 4 | 停站事件的最小停留与低速判定 |
| `boarding_tap_tolerance_sec` | 75 | 刷卡晚于发车时间仍可匹配的容差 |
| `boarding_search_sec` | 240 | 刷卡与车辆停站的最大搜索时差 |
| `dup_tap_window_sec` | 90 | 重复刷卡判定窗口 |
| `transfer_window_min` / `transfer_walk_max_m` | 25 / 800 | 换乘的时间与步行距离阈值 |
| `return_anchor_gap_min` | 45 | 启用返程锚点的最短时间跨度 |
| `walk_speed_mps` / `timing_slack_sec` | 1.2 / 90 | 步行速度与时刻容差 |
| `max_ride_min` | 120 | 单次乘车的最长时间 |
| `seat_capacity` | 80 | 车辆定员，用于满载率 |
| `time_periods` | 早间/早高峰/平峰/晚高峰/夜间 | 可增删改 |

## 8. 已知边界

- 下车站推理依赖**当日后续刷卡**；日末最后一次出行只能给先验估计，平台会如实标记。
- 环线（首末站同名）的同一卡多次乘车，站点归属可能存在歧义，已按班次切分缓解。
- 地图底图默认 Esri，若网络不可达会自动切换到 OSM；仅影响底图，不影响数据。
- 演示数据是合成的，真实数据上需要按实际 GPS 采样率调整停站阈值。

## 9. 常用命令

```bash
make setup     # 创建虚拟环境并安装依赖
make serve     # 启动控制台 http://127.0.0.1:8404
make demo      # 重新生成演示数据（含真值）
make run       # 命令行跑一次并打印核心指标
make test      # Python + 前端工具函数测试
make clean     # 清空数据库与结果（保留演示原始数据）
```
